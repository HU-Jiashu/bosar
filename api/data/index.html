    API — data and readers¶

    Rasters are GeoTIFF (float32 / complex64 / uint8) with bosar: tags; the project file is project.json. Every sensor reader returns the same contract — a scene with its metadata in SI units — so a new sensor is a reader and a fixture test, not a chain.

    Rasters and the project¶

    bosar.data.raster ¶

    Tiled GeoTIFF create / window-write / read with package-namespaced tags.

    Scope for v0.1.0: create, window writes, full reads, tags and array stats — enough for the dummy step to write a tagged, tiled product without loading it into RAM. Complex rasters (two bands + mask) and COG/geocoding arrive with the DInSAR release.

    Tags: GDAL splits metadata keys on the first colon, so bosar:units cannot be a key (the development log, probe P2). Tags therefore live in a GDAL metadata namespace (domain) named after the package and are written/read with update_tags(ns=...); TAG_PREFIX is only the display form. Products written before the rename carry their tags in the legacy namespace (bosar._legacy.LEGACY_TAG_NAMESPACES); readers merge it under the current one until 0.2.0.

    TAG_NAMESPACE module-attribute ¶

    TAG_NAMESPACE = PACKAGE

    GDAL metadata domain holding the package tags (gdalinfo -mdd bosar).

    RasterWriter ¶

    RasterWriter(path: Path, band: int = 1)

    Context manager that keeps a raster open in r+ mode and writes windows into it.

    writer[rows, cols] = block writes a host (NumPy) block; CuPy arrays are rejected with a hint to call to_host() first. Usable as out= of core.tiling.apply_tiled. Units: pixels.

    RasterSource ¶

    RasterSource(path: Path, band: int = 1)

    Lazy 2-D accessor over one band: src[rows, cols] reads only that window.

    Exposes shape and dtype so it can be passed to core.tiling.apply_tiled; close it (or use it as a context manager) when done. Units: pixels.

    read_meta(path: Path) -> RasterMeta

    Metadata of a raster, including the package tags (units: pixels).

    read_tags ¶

    read_window ¶

    read_window(

    Read a [rows, cols] window of one band (half-open pixel slices).

    create_raster ¶

    create_raster(
    path: Path,
    shape: tuple[int, int],
    dtype: Any,
    *,
    nodata: float | None = float("nan"),
    crs: Any = None,
    transform: Any = None,
    tags: Mapping[str, Any] | None = None,
    blocksize: int = 256,
    compress: str = "deflate",
    count: int = 1,
) -> Path

    Create an empty tiled GeoTIFF (blocks of blocksize px, compress) and tag it.

    Units: shape pixels; transform is an affine transform (GDAL "area" semantics apply only inside geocoding); nodata in data units. complex64 is accepted since v0.1.0 (SLC and interferogram crops); complex rasters carry no nodata value (0 + a mask band, ARCHITECTURE §3.4) and nodata is ignored for them.

    array_stats ¶

    array_stats(arr: Any) -> dict[str, Any]

    NaN-aware summary of an array: shape, dtype, min/max/mean/std, pct_valid, finite_fraction.

    Complex arrays are summarised by magnitude. Units: those of the array; percentages in %.

    build_overviews ¶

    build_overviews(
    path: Path, factors: tuple[int, ...] = (2, 4, 8, 16)
) -> list[int]

    Add internal overviews (average resampling) to a written GeoTIFF — a COG-style product (tiled + deflate + overviews) readable by any GIS at every zoom. Returns the factors used.

    write_cog ¶

    write_cog(
    path: Path,
    data: ndarray,
    *,
    transform: Any,
    crs: Any,
    nodata: float | int | None = None,
    tags: Mapping[str, Any] | None = None,
    compress: str = "DEFLATE",
    blocksize: int = 512,
) -> Path

    Write one band (or a (bands, rows, cols) stack) as a Cloud-Optimized GeoTIFF: GDAL COG driver through an in-memory GTiff, internal tiles of blocksize, overviews AUTO (nearest for integer data, average otherwise), predictor chosen by GDAL. tags go to the default metadata domain: the COG CreateCopy drops custom domains such as the package namespace (probe p13).

    Units: data in its own units; transform affine, crs any rasterio CRS input.

    read_decimated ¶

    read_decimated(
    path: Path,
    max_px: int = 2048,
    bands: tuple[int, ...] | None = None,
) -> tuple[np.ndarray, tuple[int, int]]

    A nearest-neighbour view of a raster no larger than max_px on either side, for display (the GUI's RasterView; decimation is stated there). Returns (array, full_shape): a 2-D array for one band, (bands, rows, cols) for several; GDAL uses internal overviews when a product has them. Units: those of the product; complex products stay complex.

    read_pixel ¶

    read_pixel(
    path: Path, row: int, col: int, band: int = 1
) -> Any

    The full-resolution value at integer (row, col) (pixel centre = index); None outside.

    pixel_lonlat ¶

    pixel_lonlat(
    path: Path, row: float, col: float
) -> tuple[float, float] | None

    (lon, lat) [deg] of a pixel centre of a georeferenced raster; None in radar geometry.

    GDAL "area" semantics apply here (geocode convention): the centre of pixel (r, c) is at transform * (c + 0.5, r + 0.5); projected CRSs are transformed to EPSG:4326.

    bosar.data.model ¶

    Common stack model shared by every reader: geometry, scenes, interferograms, baselines.

    v0.1.0. Every reader returns these objects so that the pipeline, the CLI and later the GUI never see a format-specific structure. Rules:

    • Units in names, SI only: metres, seconds, radians, Hz, integer days. Degrees appear only in *_deg fields that mirror what a file says (heading, centre lat/lon).
    • Nothing here loads a full-resolution array. Array access is windowed through :class:ArraySource objects (src[rows, cols]), exactly like data.raster.RasterSource.
    • dt_days is always recomputed from the two dates, never read from a file.
    • Plausibility is asserted at reader exit (:func:check_plausible): a reader that returns an implausible wavelength, incidence, range or baseline raises E204 naming file, field, expected and actual.

    DATE_RE module-attribute ¶

    DATE_RE = re.compile('^\\d{8}$')

    Acquisition dates are YYYYMMDD strings everywhere (file names, keys, JSON).

    PLAUSIBLE_WAVELENGTH_M module-attribute ¶

    PLAUSIBLE_WAVELENGTH_M = (0.02, 0.35)

    X-band (~0.031 m) to L-band (~0.24 m) with margin; SNAP MHz or GAMMA GHz slips fall outside.

    ArraySource ¶

    Bases: Protocol

    Windowed 2-D accessor: src[rows, cols] returns only that block (native byte order).

    bosar.data.annotation ¶

    Correct a stack's scalar geometry from the Sentinel-1 SAFE annotation.

    The SNAP StaMPS export (GAMMA .par) carries a nominal slant-range axis (2 m spacing, near/far = centre ∓ (N−1)/2 × 2 m, W201) and an earth_radius_below_sensor ≈ 11.5 km too small; the SAFE annotation of the same date holds the measured values. :func:apply_annotation

    • finds the swath annotation whose first-pixel slant range (c · slantRangeTime / 2) and sample count match the stack's reference scene,
    • overwrites pixel_spacing_range_m (c / (2 · rangeSamplingRate)), the near/mid/far ranges, pixel_spacing_azimuth_m, the two radii (orbit state vectors → sensor distance and ellipsoid radius under the sensor) and the incidence angles (geolocation grid),
    • re-projects every TCN baseline with the new look angle,
    • sets acq_utc of every date that has a SAFE to that SAFE's startTime (answer 2),
    • moves the W201 range-axis warning into an I201 info record carrying both B⊥ values and stamps geometry.provenance = "safe-annotation:<file>".

    Nothing changes without the call. path may be one .SAFE folder, a SAFE .zip (the annotation XML is read with :mod:zipfile, nothing is extracted) or a folder holding any number of either. Per-pixel geometry from orbits + DEM is v0.2.0.

    bosar.data.noise ¶

    Sentinel-1 thermal-noise LUTs: annotation/calibration/noise-*.xml read straight from the product zip (zipfile, nothing extracted) or from an unzipped SAFE, and evaluated on the image grid in DN^2 (the unit of |DN|^2).

    Two layouts exist (ESA MPC-0392, "Thermal Denoising of Products Generated by the S-1 IPF"; S1-RS-MDA-52-7441 §6.4.10):

    • IPF 2.90 and later (2018 on): noiseRangeVectorList - per vector an azimuthTime, an image line, the sampled pixel columns and noiseRangeLut - and noiseAzimuthVectorList - blocks (swath, firstAzimuthLine, firstRangeSample, lastAzimuthLine, lastRangeSample) with a line list and noiseAzimuthLut. The noise power is the product range(line, sample) * azimuth(line, sample); in TOPS products the azimuth factor carries the scalloping of the antenna sweep.
    • before 2.90: noiseVectorList with noiseLut - range only.

    Evaluation (:func:noise_on_grid): a range vector is interpolated linearly in sample (held constant beyond its first / last pixel); along lines either between the two vectors that bracket the line - exactly :func:bosar.data.calibration.lut_on_grid's convention, so a burst line maps onto the same absolute image line as the calibration LUT - or, for TOPS SLC, the one vector of the burst chosen by azimuth time (range_vector; :meth:NoiseLUT.range_vector_index). The second form is what SNAP's ThermalNoiseRemoval does for IW / EW SLC (one range vector per burst, held over the burst), and the only safe one: in the IPF 3.31 product of the xarray-sentinel test data each vector's azimuthTime is the azimuthTime of burst k while its line is the first line of burst k-1 (the line field is one burst early). The azimuth LUT is interpolated linearly in line inside its block (held beyond the block's first / last listed line); a pixel inside no block takes the nearest block (in lines plus samples).

    bosar.data.ceos_alos ¶

    ALOS-1 PALSAR L1.1 (CEOS SAR-CCT) reader: a product as ASF distributes it - the zip ALPSRP<orbit 5><frame 4>-H1.1__A.zip (or -L1.1.zip) or its extracted folder with VOL-, LED-, IMG-HH-, IMG-HV- (FBD) and TRL- files - opened as a :class:~bosar.data.stripmap.StripmapScene.

    The record layouts (byte offsets and widths) are those of ISCE2's alos_slc record definitions, checked against a real product (docs/data/formats.md, "ALOS-1 PALSAR L1.1"):

    • every CEOS record starts with a 12-byte header: record number (uint32), first subtype (uint8), record type code (uint8), second and third subtype (uint8 each), record length (uint32); all binary fields are big-endian; text fields are ASCII, numbers in text fields are Fortran-style (D exponents accepted);
    • the leader file is walked record by record (type code 10 = data set summary, 30 = platform position, 40 = attitude, 50 = radiometric, 60 = data quality, 200 = facility) so that a product with a different facility-record count still parses;
    • the image file: a 720-byte file descriptor, then one record per line of prefix (412) bytes of line header followed by the samples. The descriptor's bits per sample (32), samples per data group (2), bytes per data group (8) and format type code (C*8) decide the sample format: two IEEE float32 per complex sample (COMPLEX*8); a product declaring 16-bit samples would be read as two int16 (never seen; the L1.0 raw is 8-bit and is not a product of this reader).

    Conventions (docs/data/formats.md has the record table and the quirks):

    • epoch is the UTC midnight of the first line's date (year / day-of-year of its prefix); sensing_start_s is the least-squares intercept of the per-line milliseconds of day stamps against line / PRF (the stamps are integer milliseconds, half a line of quantisation; the fit recovers the start to a few microseconds); the leader's scene-centre time must agree (W222 above 2 ms, E205 above 1 s);
    • prf_hz is the leader's (mHz with decimals); the per-line PRF field (integer mHz) must not vary by more than PRF_TOLERANCE relatively (E205), any smaller variation or a difference to the leader is W221;
    • starting_range_m is the leader's range gate delay times c / 2 (the prefix's slant range to first sample is an integer metre count; W222 above 1 m, E205 above 100 m);
    • doppler: the leader's cross-track Doppler centroid polynomial is in Hz per range pixel (f = c0 + c1 p + c2 p^2, p the 0-based sample index; ISCE2 ALOS_SLC.py uses it as dopplerVsPixel; checked on a real product by the correlation Doppler estimator at near, mid and far range); it is converted to slant range with p = (r - r0) / dr so that the oversampled FBD grid keeps the same polynomial;
    • the orbit: the platform position record's state vectors (ECR = Earth-fixed, metres, m/s, 60 s apart) on the scene epoch, densified to ORBIT_SPACING_S with the 8th-order Lagrange interpolation so that the chain's cubic Hermite stays below a millimetre (at 60 s it would be 0.3 m);
    • look_side from the leader's sensor clock angle (+90 deg = right, as ISCE2 reads it), checked against the geolocation of the first line's centre pixel (prefix latitude / longitude) relative to the orbit's cross-track direction (E204 when they disagree); pass_direction from the orbit's vertical velocity at mid scene;
    • calibration_db: sigma nought = 10 log10 |DN|^2 + CF - A with the leader's calibration factor CF (-83.0 dB since 2009-04-09, Shimada et al. 2009, IEEE TGRS 47(12)) and the L1.1 conversion A = 32.0 dB, i.e. -115.0 dB; both parts are in extra;
    • mode FBS (32 MHz sampling, 28 MHz chirp, HH) or FBD (16 MHz, 14 MHz, HH + HV); the mode comes from the sampling rate, the chirp bandwidth (|rate| x pulse length) is recorded in extra. oversample_to_fbs=True serves an FBD scene on the FBS grid (:func:bosar.core.range_oversample.oversample_range): n_samples, the range spacing and the sampling rate reflect the oversampled grid, the bandwidth stays 14 MHz.

    read_slc(window) reads only the requested lines (one seek per line, prefix skipped) and samples; a zip is read in place when ASF's stored members allow it (one file handle, absolute offsets), a deflated member through zipfile's seekable stream (slow: unzip it first).

    ALOS-2 PALSAR-2 L1.1 is the same CEOS product with JAXA's record layout (PALSAR-2_xx_Format_CEOS_E.pdf, checked on the free Greenland FBS pair): the scene id is ALOS2<orbit 5><frame 4>-<YYMMDD> followed by the product id <mode><L|R><level><option> <projection><A|D> (FBSR1.1__A); the leader's data set summary, platform position and radiometric records have the ALOS-1 offsets (the mission id says ALOS2); the signal data record's prefix is 544 bytes with the ALOS-1 fields to byte 216 plus the microseconds of day at bytes 84-92, which give the line times exactly (the millisecond fit stays a check); the leader's range gate delay is not the delay to the first sample (132.5 us where the prefix's slant range says 5056 us: the gate is counted inside a pulse interval), so the prefix's integer metres are the starting range; the cross-track Doppler polynomial is in Hz per pixel as on ALOS-1 and agrees with the leader's a + b R[km] centre-frequency fields (checked: W222 when they differ by more than :data:DOPPLER_CHECK_HZ). The mode comes from the product id (:data:ALOS2_MODES: nominal chirp bandwidth and range sampling rate per mode); the spotlight (SBS) and ScanSAR (WBS / WBD / WWS / WWD / VBS / VBD) products are recognised and refused (E205, the mode named): they are not stripmap scenes (a ScanSAR product's per-scan image files IMG-<pol>-<tail>-F<n> belong to its LED-<tail> product, and one image file per scan is refused as ScanSAR whatever the product id says). The range bandwidth is the leader's chirp |rate| x pulse length when it is plausible against the mode's nominal value (:data:ALOS2_BANDWIDTH_TOLERANCE; 24.9 MHz on the Greenland FBS scenes where the nominal is 28 MHz), else the leader's total processor bandwidth in range, else the nominal value (W222); a plausible total more than :data:BANDWIDTH_CHECK_REL below a plausible chirp is used instead of it (W222: the processed spectrum is no wider than either); the nominal value, the leader's total and the source are in extra. oversample_to_fbs has no effect on an ALOS-2 scene (its FBD shares the FBS sampling). The scene carries mission="ALOS-2", sensor="PALSAR-2", the L band wavelength 0.2425 m (the L-band quality profile follows).

    Both missions: without pol the scene is the product's HH image, else its VV image (PALSAR-2 VV and VV + VH products), else its first polarisation (:func:default_polarisation). A folder holding several products (two zips extracted into one folder) is never merged: a member file opens its own product, the folder itself is refused (E101). Only a LED- file with at least one IMG- file of the same name tail makes a product: a GDAL .aux.xml sidecar next to an image file is not one.

    bosar.data.asar ¶

    ENVISAT ASAR IMS and ERS-1/2 SAR IMS products in the Envisat product format.

    One parser serves ASA_IMS_1P...N1 (ENVISAT ASAR, image mode single-look complex) and SAR_IMS_1P...E1 / .E2 (ERS-1 / ERS-2 AMI image mode, as ESA now distributes them from the same processor, SOFTWARE_VER="ASAR/7.00"). Every binary field is big-endian; offsets below are bytes from the start of the record. The layouts were taken from ISCE2's EnviSAT_SLC.py (MPH / SPH / DSD scheme; the first offsets of the processing-parameter, Doppler and geolocation records) and completed on the author's 26 products (docs/data/formats.md); the ESA product specification (PO-RS-MDA-GS-2009 vol. 8) was not on disk.

    File layout::

    MPH   1247 bytes, ASCII ``KEY=value`` lines (quoted strings, numbers with ``<unit>``)
SPH   SPH_SIZE bytes: ASCII keywords, then NUM_DSD data-set descriptors of 280 bytes each
      (DS_NAME, DS_TYPE, FILENAME, DS_OFFSET, DS_SIZE, NUM_DSR, DSR_SIZE)
ADS   annotation data sets at their DS_OFFSET (file offsets)
MDS1  NUM_DSR line records of DSR_SIZE = 17 + 4 * samples bytes

    Records read (offset: field, type, unit):

    • MAIN PROCESSING PARAMS ADS (one DSR of 10069 bytes on these products; 2009 on products of processors before 6.02 - same leading layout, not verified here): 0 first_zero_doppler_time MJD; 13 last_zero_doppler_time MJD; 41 swath (3 chars); 44 range_spacing f32 m; 48 azimuth_spacing f32 m; 52 line_time_interval f32 s; 56 num_output_lines u32; 60 num_samples_per_line u32; 64 data_type (5 chars, SWORD); 73 time_diff_zero_doppler f32 s; 120 fourteen processing flags u8; 703 prf_value[0] f32 Hz; 743 tx_pulse_bw_value[0] f32 Hz; 975 first_proc_range_samp u32; 979 range_ref f32 m (range-spreading-loss reference); 983 range_samp_rate f32 Hz; 987 radar_freq f32 Hz; 991 num_looks_range u16; 993 filter_range (7 chars); 1000 filter_coef_range f32; 1004 look_bw_range[5] f32 Hz; 1024 tot_bw_range[5] f32 Hz; 1264 num_lines_proc u32; 1268 num_look_az u16; 1270 look_bw_az f32 Hz; 1274 to_bw_az f32 Hz; 1278 filter_az (7 chars); 1285 filter_coef_az f32; 1289 az_fm_rate[3] f32 (Hz/s, Hz/s^2, Hz/s^3 in two-way time); 1301 ax_fm_origin f32 ns; 1305 dop_amb_conf f32; 1377 proc_scaling_fact f32; 1381 ext_cal_fact f32 (the external calibration constant K); 1509 output_statistics[2] (4 f32 each); 1541 avg_scene_height_ellpsoid f32 m - the ellipsoidal height the geolocation grid was computed at (2527 m on the ASAR Mexico City products, 0 on the ERS ones; ISCE2 reads 1537, four bytes early, as it reads the state vectors at 1761); 1765 + 36 k (k = 0..4) orbit state vectors: MJD, then x, y, z as i32 in 1e-2 m and vx, vy, vz as i32 in 1e-5 m/s, Earth-fixed frame (a slot that is blank - spaces, 0xFF or zeros, as the spare areas of the record are space-filled - is skipped; all 26 products fill all five).
    • DOP CENTROID COEFFS ADS (55 bytes): 0 zero_doppler_time MJD; 13 slant_range_time f32 ns (two-way origin); 17 dop_coef[5] f32 in Hz, Hz/s, ... Hz/s^4 of tau - tau0 in seconds; 37 dop_conf f32; 41 dop_conf_below_thresh u8; 42 delta_dop[5] i16.
    • GEOLOCATION GRID ADS (NUM_DSR records of 521 bytes): 0 zero_doppler_time MJD of the record's first line; 13 line_num u32 (1-based); 17 num_lines u32; 21 sub_sat_track f32 deg; 25 samp_numbers[11] u32 (1-based); 69 slant_range_times[11] f32 ns (two-way); 113 angles[11] f32 deg (incidence); 157 lats[11] i32 1e-6 deg; 201 longs[11] i32 1e-6 deg; 267 last_zero_doppler_time MJD (line line_num + num_lines - 1); 279 .. 499 the same five arrays for that last line.
    • CHIRP PARAMS ADS (1483 bytes): 13 swath, 16 polarisation (3 chars each); 19 chirp_width f32 samples; 23 chirp_sidelobe, 27 chirp_islr f32 dB; 31 chirp_peak_loc f32; 35 re_chirp_power, 39 elev_chirp_power f32 dB; 43 chirp_quality_flag u8; 44 ref_chirp_power f32 dB; 48 normalisation_source (7 chars). Informational only.
    • MDS1 line record: 0 zero_doppler_time MJD; 12 quality_flag u8; 13 line_num u32 (1-based); 17 samples as big-endian int16 pairs (I, Q), DATA_TYPE="SWORD".

    MJD fields are 12 bytes: days since 2000-01-01 00:00:00 UTC as signed i32 (negative for the 1990s ERS scenes), seconds u32, microseconds u32.

    Geometry convention: the products are focused to zero Doppler (ALGORITHM="RAN/DOP", lines stamped with zero-Doppler times): the scene's :class:~bosar.data.stripmap.DopplerPolynomial is zero and the processed Doppler centroid of the DOP ADS goes to extra["processed_doppler_centroid"] for the resampler. The acceptance test of this claim and of the parser is rdr2geo of every geolocation-grid tie point from the product state vectors against the tie point's own lat / lon, both at the product's avg_scene_height_ellpsoid (tests/test_integration_asar_real.py; the measured agreement is in docs/data/formats.md: about 1 m on all 26 products).

    Orbit: the five MPP state vectors span exactly the frame (first to last line, ~4.6 s apart); they are extended by orbit_margin_s on both sides with :func:bosar.core.orbit.extend_orbit (two-body + J2 in the Earth-fixed frame) so that the geometry kernels have a margin, and replaced by a DORIS / PRC file when orbit_file is given (:mod:bosar.data.doris). Such a file must agree with the product's own vectors at mid scene: W223 beyond 100 m, refused (E204) beyond 1 km - the ERS-1 and ERS-2 PRC files of a tandem day cover the same times 11 950 km apart.

    Calibration: calibration_db = -10 log10(K) with K = ext_cal_fact; the full ESA convention for single-look complex products (Rosich & Meadows 2004, ENVI-CLVL-EOPG-TN-03-0010) is sigma0 = |z|^2 / K * (R / range_ref)^3 * sin(incidence) with the per-pixel terms left to the caller (extra["calibration"] carries K and range_ref). Not verified on a target.

    bosar.data.ionex ¶

    IONEX 1.0 global ionosphere maps and the single-layer ionospheric phase of an interferogram.

    Format (Schaer, Gurtner & Feltens 1998, "IONEX: The IONosphere Map EXchange Format Version 1"). Fixed columns; every header and map record carries its label in columns 61-80. Header: EPOCH OF FIRST MAP / EPOCH OF LAST MAP (6I6, UTC), INTERVAL (I6, s), # OF MAPS IN FILE, MAPPING FUNCTION (COSZ / QFAC / NONE), BASE RADIUS (F8.1, km), MAP DIMENSION (2 for a single layer), HGT1 / HGT2 / DHGT, LAT1 / LAT2 / DLAT, LON1 / LON2 / DLON (2X,3F6.1: km, degrees; latitudes usually run north to south, DLAT < 0), EXPONENT (I6, default -1), optional START OF AUX DATA ... END OF AUX DATA blocks (differential code biases), END OF HEADER. Data: START OF TEC MAP / EPOCH OF CURRENT MAP / per latitude a LAT/LON1/LON2/DLON/H record (2X,5F6.1) followed by the values of that latitude band, 16 per line (I5), END OF TEC MAP; the same for RMS MAP (and HEIGHT MAP in 3-D files, not supported). Values are in units of 10**EXPONENT TECU (an EXPONENT record inside a map overrides the header's for that map); 9999 = no value. Plain text or gzip (.gz); the Unix compress files (.Z) of the old CODE naming are refused with a hint.

    Interpolation (Schaer et al. 1998, eqs. 1-4). Space: bilinear between the four grid nodes around the point. Time: the maps are tied to the Sun rather than to the Earth, so between the maps E_i at T_i and E_i+1 at T_i+1 the value at (lat, lon, t) is

    E = (T_i+1 - t) / (T_i+1 - T_i) * E_i(lat, lon + w (t - T_i))
    + (t - T_i) / (T_i+1 - T_i) * E_i+1(lat, lon + w (t - T_i+1))

    with w = 360 deg / day (the rotated-map interpolation; a point keeps its local solar time).

    Single-layer model. All electrons sit in a thin shell at height H (HGT1 of the header, 450 km for the CODE / IGS maps) above a sphere of radius R (BASE RADIUS). The line of sight from a ground point at zenith angle z pierces the shell at the zenith angle z' with sin z' = R / (R + H) sin z and the earth-central angle psi = z - z' from the ground point, toward the sensor; slant TEC = VTEC(pierce point) / cos z'.

    Interferometric phase and its sign. Bosar's SLC phase is -4 pi R_phase / lambda = -4 pi f R_phase / c (ARCHITECTURE §5). The ionosphere advances the carrier phase: the phase path is R_phase = R - K STEC / f^2 (K = 40.31 m^3 s^-2, STEC in electrons m^-2), so phi_slc(f) = -4 pi f R / c + 4 pi K STEC / (c f). The interferogram is ref * conj(sec):

    phi(f) = 4 pi f (R_sec - R_ref) / c  +  4 pi K (STEC_ref - STEC_sec) / (c f)
    • the second, dispersive term is :func:iono_phase_rad: 4 pi K 1e16 dSTEC / (c f) with dSTEC = STEC_ref - STEC_sec in TECU (1 TECU at 5.405 GHz: 3.13 rad). More electrons on the reference date read like a longer range on the secondary date: positive phase. The split-spectrum estimate (core.iono.split_spectrum_phases) returns the b / f0 part of phi(f) = a f + b / f of the same interferogram, i.e. exactly this term at the carrier, with the same sign (tested on SLCs simulated from the formula above).

    CODE final GIMs (http://ftp.aiub.unibe.ch/CODE/YYYY/): COD0OPSFIN_YYYYDDD0000_01D_01H_ GIM.INX.gz (25 hourly maps, 00:00 to 24:00 UTC) since GPS week 2238 (2022-11-27), CODGDDD0.YYI.Z before. :func:code_gim_candidates names them; nothing here downloads.

    Units: degrees for latitude / longitude, radians for angles in computations, metres, seconds, TECU (1e16 electrons m^-2). Re-implemented from the format description; no code copied.

    bosar.data.doris ¶

    Precise orbits for ENVISAT and ERS: DORIS files in the Envisat format and the ERS PRC files of D-PAF.

    DORIS (DOR_VOR_AX... precise, DOR_POR_AX... preliminary; ESA now delivers the reprocessed ERS-1/2 orbits in the same form - the ORBIT STATE VECTOR 1 DSD of the ERS IMS products names DOR_VOR_AXVF-P1996...): an MPH (1247 bytes) and SPH with one measurement data set (DS_TYPE=M, DS_NAME="DORIS PRECISE ORBIT" or "DORIS PRELIMINARY ORBIT") of ASCII records, one state vector per record::

    07-MAR-2003 16:35:28.000000  <delta UT1 s>  <abs orbit>  X Y Z [m]  VX VY VZ [m/s]  <quality>

    Fields are read by whitespace splitting (tokens 0-1 the UTC time, 4-6 the position, 7-9 the velocity, 10 the quality flag), as ISCE2's DOR class does; the Earth-fixed frame of the file is the one the products' state vectors use. Read on real DOR_VOR_AXVF files of the public STEP mirror for the ENVISAT ASAR pair: 3-7 cm from the products' own vectors at mid scene.

    PRC (D-PAF / DLR precise orbits for ERS-1/2, "DGM-E04" products): fixed records of 130 ASCII bytes. Reconstructed from ISCE2's Orbit/PRC.py (the format description is not on disk) and confirmed on ESA's PRC_<yymmdd>_<orbit>_rev2 files for the ERS tandem pair (about 10 m from the products' vectors, the +0.5-day convention borne out): STATE record (columns 0-6): bytes 6-12 and 12-18 the first / last epoch in 0.1 days since J2000, bytes 47-52 the TDT - UTC offset in ms; STTERR records (terrestrial frame): bytes 14-20 the day in 0.1 days since J2000 (12:00 TDT of 2000-01-01, so +0.5 day gives days since 2000-01-01 00:00), 20-31 seconds of day in microseconds (TDT), 31-43 / 43-55 / 55-67 x, y, z in mm, 67-78 / 78-89 / 89-100 vx, vy, vz in micrometres per second, byte 127 the quality character. UTC = TDT - offset. STTINE (inertial) records are skipped. Unix-compress .Z files are refused with a hint.

    Satellite: OrbitRecords.satellite is "ENVISAT" / "ERS1" / "ERS2" or None when the file does not say. PRC: the lead DSIDP record (DSIDP ERS1.ORB.PRC on ESA's PRC_<yymmdd>_<orbit>_rev2 files), else the COSPAR id of the state-vector records (bytes 6-13: 9105001 ERS-1, 9502101 ERS-2). DORIS: the SPH descriptor (ORBITE POE_REST SAT ENV1 on the STEP mirror's DOR_VOR_AX files). The STEP mirror keeps the ERS-1 and ERS-2 PRC files of a year side by side, and in the tandem months both cover the same times: a folder lookup must filter by satellite (orbit_files_covering).

    Units: metres, metres per second, UTC datetime64[us].
