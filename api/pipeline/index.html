    API — pipeline¶

    Every processing operation is a Step (a parameter model, what it requires, what it produces, run(ctx)) registered in bosar.pipeline.registry. The Runner — not the step — does the timing, the logging, the project-file updates and the garbage collection of intermediates.

    Steps and the runner¶

    bosar.pipeline.step ¶

    The Step contract (docs/ARCHITECTURE.md §3.3) and what a step receives and returns.

    A step declares kind, version (bump when the algorithm changes → cached outputs invalid), a pydantic Params model, the product kinds it requires and the (kind, tier) pairs it produces; run(ctx) does the work. Timing, logging, project updates and garbage collection belong to the Runner, never to the step.

    Step ¶

    Bases: Protocol

    Contract every processing operation implements (registered with register_step).

    Optional hook: produces_for(params) -> list[(ProductKind, Tier)] (a classmethod or staticmethod) narrows produces to what this parameter set will actually write; every entry must also appear in produces. The Runner checks and records the narrowed list. A produces kind may be a family pattern (amp_db/*: one product per date); the Runner then requires at least one matching output and gives every member its tier.

    bosar.pipeline.runner ¶

    The Runner: the only place that times, logs, updates the project and garbage-collects.

    Sequence: validate params → run logger + run_start → backend (W401) → offline preflight (blocking → run_end(blocked) + E701, project untouched) → interrupted-step recovery (E802 + W104) → skip rule (W101) → step record running + save → step_start → Step.run inside a warnings capture (W000) → outputs verified (E607) and registered → step_end (seq) → done + log_seq + save → gc → guarded hooks (W803) → run_end + report. On failure the record is written before the project is saved, partial tier-2 outputs are kept and listed, every post-failure action is guarded (W802 never masks the original error) and StepFailedError (E801) is raised with the original exception as __cause__.

    run_chain ¶

    run_chain(
    steps: Sequence[ChainStep],
    *,
    force: bool = False,
    clean_on_failure: bool = False,
) -> list[StepRecord]

    Run steps in order under ONE run log/report; garbage-collect once at the end.

    A standalone run() in storage_mode=minimal deletes a tier-2 product as soon as every dependent step known so far is done; a chain declares its steps up front, so intermediates survive until the last step and are collected together.     Products, planning, storage¶

    bosar.pipeline.products ¶

    Product references: a tier-1 product that points at an imported stack's file without a copy.

    ifg_import records the SNAP .diff of a pair — 2.5 GB on the full stack — as products/ifg_flat/<step>.ref.json; later Steps open it with :func:open_source, which returns a windowed accessor (a :class:RasterSource for GeoTIFF products, a :class:StackMember for references) so kernels never know where the pixels come from.

    StackMember ¶

    StackMember(

    Windowed complex64 accessor over one interferogram or scene of an imported stack.

    Opens the stack on construction and closes it with :meth:close; exposes the stack's geometry and the member's dates so a Step can fetch the SLC powers and the geometry layers of the same grid.

    bosar.pipeline.plan ¶

    Declared plans of multi-command chains.

    A chain such as bosar sbas prep → bosar pipeline sbas runs over several commands and processes. In storage_mode=minimal the Runner collects a tier-2 product as soon as every known dependent step is done - a dependent that has not been created yet does not count, so the multilooked interferograms of a network were deleted before its unwrap phase, the flattened stack before the PSI step, and so on. A plan declares the ordered steps of a chain up front (step_id, kind, requires) in project.json under aux.plans[<name>]; a declared dependent that is not done yet keeps the products of the steps it requires. The plan is removed when its last step is done (complete_plan), and the normal collection follows.

    A time-series step run in a minimal-storage project outside any declared plan is refused with E310 (:class:bosar.errors.ChainUndeclaredError): the one-line remedy is bosar project new --storage-mode full or one of the chain commands, which declare.

    bosar.pipeline.storage ¶

    StorageManager: registers products with their tier and garbage-collects by the tier rules.

    Rules (ARCHITECTURE §3.2, author decisions D-tier): tier 3 of a step is deleted when the step ends — also when it fails; tier 2 is deleted only in storage_mode="minimal" and only when the producing step has at least one dependent and every dependent is done (zero dependents would be vacuously "all done"); tier 1 is never deleted; nothing outside the project directory is ever touched. Files are deleted one by one (safe_unlink), never with a recursive remove.

    The installed build and its plug-ins¶

    bosar.build ¶

    The frozen build and its plug-ins.

    A PyInstaller one-folder build carries bosar_build.json next to the collected modules (sys._MEIPASS): the build id, the version, the platform tag, the git commit, the build time, whether the bundled SNAPHU was built without CS2. bosar preflight and bosar version report it; a source checkout reports none.

    Plug-ins are wheels unpacked under <user data dir>/bosar/plugins/<name>/site-packages by bosar gpu install (:mod:bosar.plugins); :func:activate_plugin appends such a folder to sys.path before the package that needs it is imported (CuPy in backends). The bundle's own packages stay ahead on the path, so a plug-in never shadows them.

    module_request ¶

    module_request(
    argv: Sequence[str],
) -> tuple[str, list[str]] | None

    (module, arguments) when a frozen executable is called as if it were the interpreter - bosar.exe [-X <opt>]... -m <module> [arguments] - which is what cuda-pathfinder's canary probe (sys.executable -m cuda.pathfinder..., CuPy 14) and Bosar's own child processes (sys.executable -X utf8 -m bosar ...) do; None for an ordinary command line. -X options are accepted and dropped here: the bootloader cannot take interpreter options from the command line, the frozen interpreter gets them from the build - bosar.spec passes ('X utf8', None, 'OPTION') to both executables, so a build runs in UTF-8 mode like python -X utf8 (the bootloader's isolated configuration ignores PYTHONUTF8) - and :func:utf8_requested tells :func:run_module_request that the caller asked for UTF-8. Units: none.

    utf8_requested ¶

    utf8_requested(argv: Sequence[str]) -> bool

    True when the interpreter-style command line asks for UTF-8 mode: -X utf8 (or -X utf8=1; the last utf8 option wins, as in CPython) among the -X options before -m. Units: none.

    ensure_utf8_streams ¶

    ensure_utf8_streams() -> list[str]

    Switch sys.stdout / sys.stderr to UTF-8 when the interpreter is not in UTF-8 mode - the fallback for a bundle whose interpreter did not get the spec's X utf8 option: Bosar's parents read their children's output as UTF-8 (-X utf8 children). Each stream keeps its error handler (reconfigure(encoding=...) alone would reset it to strict); one on strict gets the handler of UTF-8 mode - surrogateescape for stdout, backslashreplace for stderr - so a lone surrogate (an undecodable file name) never raises. Streams without reconfigure (None in a windowed build, a test capture) are left alone. Returns the names of the streams switched. Units: none.

    run_module_request ¶

    run_module_request(
    module: str,
    arguments: Sequence[str],
    *,
    utf8: bool = False,
) -> int

    Run module as python -m module arguments would inside this process (the frozen executable standing in for the interpreter), through :func:runpy.run_module with sys.argv set - the package itself too: bosar/__main__.py runs the CLI (the spec bundles it), so this module never imports the CLI (build sits below cli in the layering). utf8 (the caller gave -X utf8, :func:utf8_requested) makes sure the standard streams write UTF-8 even when the interpreter is not in UTF-8 mode (:func:ensure_utf8_streams).

    Returns the exit code as the interpreter would make it: the module's SystemExit code (None is 0; a message other than an integer goes to stderr and gives 1), 0 when it returns, 1 with one line on stderr when the module cannot be found or is a package without __main__. An exception raised while the module runs propagates (a traceback, exit code 1). Units: none.

    bosar.plugins ¶

    Plug-ins of a frozen build: wheels fetched from PyPI and unpacked under the user's data folder. The first and only plug-in is the GPU backend: cupy-cuda12x with its [ctk] extra (the NVIDIA runtime wheels), which the installers do not carry.

    No pip inside a PyInstaller build - so this module resolves the wheels itself: the PyPI JSON API lists every file of a release; the newest release that has a wheel compatible with this interpreter (packaging.tags.sys_tags) is chosen; the wheel is downloaded, its SHA-256 checked against the index, unpacked; its Requires-Dist lines are followed (markers evaluated with the requested extras) except for the distributions the application already bundles. A manifest records what was unpacked. Network code lives here, never in core.

    The functions take their fetch and download callables as parameters so the tests run the whole resolution on a fake index without a socket.
